## Limits and what a future round must add

The audit reads declarations and source bytes, not instrument behavior (`check_scripts` calls `ast.parse`; `price_row` applies textual checks). A plausible lie in a nonempty pin or scope cell can pass. An entry command may name an existing parseable file yet fail to run in its advertised mode. A script can return exits or emit verdicts contradicting its declared map. The historical manual evidence for that distinction is `.ufo/waves/round-72/w1/RegistryAuditR72.md`, F1–F6 and F9; this audit must not inherit the manual review's stronger evidential claim.

A future round must add controlled execution of the exact declared argv, independent comparison of observed exit/output classes with the verdict map, recomputation of declared pins from their referents, and observed write boundaries compared with the scope cell. It must explicitly reject malformed registry lines rather than dropping them, and test misleading-but-plausible declarations and contradictory erratum prose. These are prospective capabilities, not changes to the frozen predicate (`plans/round-73-claims.md`, Kill rule).

Further scope boundaries are visible directly in `parse_rows`, `selftest_unbacked` and `check_errata`: only retained rows enter the audit universe; flag substring presence is not CLI support; a correct revision token beside contradictory attribution can satisfy item-local presence. The audit reads the supplied working tree; its docstring's “committed bytes” wording does not itself pin those bytes to a revision. A future execution gate needs an explicit clean, revision-bound input tree.
