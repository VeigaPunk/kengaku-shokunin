## Counterexample / limits

No host escape or production-side effect was found. The strongest boundary weakness is resource containment: probe `harness()` has a per-sandbox-call timeout of 1800 seconds, but the sandbox argv sets no explicit CPU, memory, process-count, or aggregate disk quota; observed RLIMIT CPU/address-space are unlimited, process limit 122865, file limit 274877906944 bytes. A malicious/unbounded workload could consume CPU/memory or fill the `--work` filesystem before timeout. The fixed case recipes at this revision are static and bounded, so this is a sandbox-hardening limitation, not evidence that the frozen probe currently executes arbitrary package content. `--unshare-pid` limits visibility, not host-wide resource consumption. No full exhaustion attempt was made.

The inherited stdin discrepancy versus the counter is observed, but appears non-exploitable for actual candidate execution due to both DEVNULL boundaries described above. No external source URL was opened, so there is no external quote/access-date citation.

## Smallest safe correction

For any future change that executes untrusted/dynamically supplied cases, apply a host-compatible per-run resource boundary (prefer a controlled cgroup for CPU/memory/pids/disk; a fixed low `RLIMIT_NPROC` is specifically unsafe on this host due to its uid-wide thread count). Also set `stdin=subprocess.DEVNULL` on the outer probe `subprocess.run` to make the boundary explicit and consistent with the counter. This review does not establish a need to change the static frozen cases or imply claim admission.
