## 2. What the primary sources say about the mechanism

Commands: `read https://www.sqlite.org/wal.html`, `read https://www.sqlite.org/fileformat2.html`, `gh api repos/sqlite/sqlite/contents/src/wal.c` (mirror HEAD `0b97f1b1`, 2026-10-26; sha256 of the file `0be881c2…`).

- wal.html §4 (The WAL File): "Usually, the WAL file is deleted automatically when the last connection to the database closes." Same section: "The only safe way to remove a WAL file is to open the database file … then immediately close the database using sqlite3_close()". So the docs call an open-then-close the *safe* removal route — the same step the task's plain read-write query performs.
- wal.html §6: "When the last connection to a database closes, that connection does one last checkpoint and then deletes the WAL and its associated shared-memory file." §3.1: automatic checkpoint "when the last database connection on a database file closes."
- fileformat2.html §4.1: header magic is `0x377f0682` or `0x377f0683`; a frame is valid only if salts match and the cumulative checksum matches. An XOR-`0x42` file starts `75 3d 44 c0` (the oracle's own `expected_xor="753d44"`), so it has neither.
- `src/wal.c` `walIndexRecover` (comment around line 1472-1475): "if the 'magic' value is invalid, ignore the whole WAL file" → `goto finished` with zero frames; and `sqlite3WalClose` (lines 2599-2646): after an EXCLUSIVE lock and a passive checkpoint with `rc==SQLITE_OK`, `isDelete = 1` unless `SQLITE_FCNTL_PERSIST_WAL` is set, then `sqlite3OsDelete(pWal->pVfs, pWal->zWalName, 0)`.
- **[INFERENCE, assembled from the three facts above]**: an undecryptable WAL is read as "no valid frames", the checkpoint copies nothing, and the closing connection unlinks the file. The docs never say this in one sentence, so the sqlite.org page alone does **not** carry the trap; the observed receipts do (the lane's probe case `plain-read-then-solve`, `db-wal-probe.txt:10`; the trace below).

Observed instance in the PR #3 attachment (`https://github.com/user-attachments/files/28821245/pr3-db-wal-recovery.zip`, 953,395 bytes, downloaded and unzipped; 5 trials, agent `claude-code`, model `anthropic/claude-sonnet-4-6`): rewards per trial `KX7negG 0`, `QUmWRrt 1`, `nZx9NaS 0`, `oihh96t 0`, `vdtktau 1`; verifier `7 failed` for the three zeros, `7 passed` for the two ones; the passing runs took 19 and 21 steps, the failing ones 88-96. In `oihh96t/trajectory.json` step 7-8 are `sqlite3 /app/main.db "SELECT * FROM sqlite_master;"` / `"SELECT * FROM items ORDER BY id;"`, step 10 `xxd /app/main.db-wal` returns `No such file or directory`, and step 20 reads: "The WAL file disappeared after SQLite accessed the database." Commands: `python3` over `trajectory.json`, `result.json`, `verifier/test-stdout.txt`. This is five runs of one model, not a rate.
