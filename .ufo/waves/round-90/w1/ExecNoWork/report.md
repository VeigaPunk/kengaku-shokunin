## 2. Ledger-only C3 variants (scratch fixture repos at BASE + appended rows)

Fixture rows were generated by `receipts/mkrows.py` from the BASE ledger: one resolution row per pending finding (`status=closed`, `close="ledger-only control: marked closed by fiat, no work performed"`, `check=null` so the base row's check still runs, `supersedes=<id>`), and for the seed variant seven base rows `FAKESEED-83…FAKESEED-89` (`opened_round` 83..89, `status=closed`, `source=corpus/routed-findings.jsonl:1`, no check).

What this shows:

1. **Expected result holds:** rows carrying checks produce `check-failed` defects and rc1. In fx1, 21 of the 32 checked closes fail (the other 11 pass: `R42-R3-09, -33, -34, -37`, `R45-S5-7b..e`, `R51-R2..R4`). The 11 passing closes are honest only if their checks are non-vacuous; I did not audit that (not in this item).
2. **Finding (HIGH, operability): `freeze=admitted` is printed while the predicate fails.** `refuse` is computed only from pending rows; failed closed-row checks do not affect the freeze verdict, only `PREDICATE`. The claims wire the freeze citation to `freeze=admitted`. A round can therefore cite an admitted freeze while closes are false to the tree. The kill rule catches it only if someone reads the PREDICATE line.
3. **Finding (HIGH, prediction failed): the gate DOES count unverified seeds.** `seeds = count(base rows with opened_round in 83..89)`. Seeds are validated only for schema and for a non-blank line at `<path>:<line>`; no check, evidence or content match is required. Seven fabricated rows raise `seeds_83_89` from 0 to 7 (fx3). The predicate's "≥ 6 seeds" can be met by fabricated rows. [INFERENCE from code] a seed carrying a passing check (e.g. `true`) would also satisfy it, since the check is not tied to seeds.
4. **Finding (MEDIUM, operability): every superseded check runs twice.** The check loop visits both the base row (resolved via `supersedes_by_target`) and the resolution row. In fx2 the output has 44 `check-failed` lines: 42 are duplicates of 21 `CTRL1-*` ids, and the 2 base-closed failures (`R42-R2`, `R82-V8`) appear once. `checks_run` is inflated to 162 (98 closed-base + 2×32). Verdict unchanged; the defect count and check count are misleading.
5. **Finding (MEDIUM, design): the gate runs checks against the lane *working tree*, not `--rev`.** `run_check(command, lane.root)` ignores the revision. `--rev BASE` therefore reports BASE ledger rows but tree-state checks. The docstring says this is deliberate ("the tree is the surface a round-close triage verifies"); the claims' wording ("at the measured revision") does not say so. A dirty tree changes the verdict. Also: R82-V8 result depends on the sibling fleet repo (item 1 above).
6. Closures without a `check` have no evidence test: `close` is free text. Only the malformed R82-F1 resolution in the fixtures has no check and closes silently.
