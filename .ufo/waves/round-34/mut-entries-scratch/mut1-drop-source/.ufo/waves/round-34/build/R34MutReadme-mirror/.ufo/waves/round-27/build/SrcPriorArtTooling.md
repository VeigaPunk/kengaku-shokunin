## Findings

- **Novelty verdict — hold at 7; no +1.** “A separately designed parser-policy comparison” is not novel in kind: published work re-scores fixed generations with alternative extractors and quantifies score effects; the cybersecurity audit also reports per-item disagreement between two extraction rules. I found no evidence for the exact R27 deliverable (nine pre-registered policies, full 9×9 *verdict* matrix, fixed grader, exact CIs, strata/cell shifts, and this 1,964-record population). That is a specific breadth/statistical-protocol extension, not a new comparison construct. The pre-registration itself appropriately predicts novelty held at 7 (claims §C1, lines 73–78); `corpus/README.md:260` calls the parser-policy comparison open, but the broader construct is already published.

- **lm-evaluation-harness 0.4.13 (PyPI release 2026-08-31): direct tooling prior art.** Official docs: “Tasks can define multiple filter pipelines that run on the same model outputs.” URL `https://lm-evaluation-harness.readthedocs.io/writing_tasks/filters/`, section “Multiple filter pipelines” (access 2026-10-21). Downloaded official wheel SHA-256 `5daaa1973bf874005f64f28d3834b875f6886f0d6475878e6a6c821994a5286a`; `lm_eval/api/filter.py:34-56` defines `FilterEnsemble`, applies its steps sequentially, then stores the result by distinct pipeline name on each same instance. `lm_eval/api/task.py:757-769` builds all named pipelines from `filter_list`. `tasks/gsm8k/gsm8k.yaml:32-43` concretely defines `strict-match` and `flexible-extract`; latter uses `group_select: -1`. `filters/extraction.py:47-49` applies this index to `findall` results, so default 0 vs -1 selects first vs last match. This is alternative extraction and per-pipeline scoring, not an agreement matrix.

- **Inspect AI 0.3.282: offline rescoring and multiple scorers.** Docs say: “You may choose to use a different scorer than the task scorer to score a log file.” URL `https://inspect.aisi.org.uk/scoring-workflow.html.md`, “Score Command” (access 2026-10-21). The same section documents `inspect score ... --scorer ...`; “Multiple Scorers” docs say individual sample scores can be preserved: `https://inspect.aisi.org.uk/multiple-scorers.html.md`. PyPI version observed 0.3.282 (2026-10-19); extracted wheel source confirms CLI `--scorer` at `inspect_ai/_cli/score.py:69`. Pattern/match/answer scoring are documented extraction/match modes at `scorers.html`. This is general rescoring infrastructure, not an extraction-agreement analysis.

- **Promptfoo 0.124.1: stored-output assertion path.** Official package CLI code requires `--model-outputs` with `--assertions`, reads the JSON file, and maps outputs into tests: extracted npm package `dist/src/main.js:2787-2792`; package version from npm registry `0.124.1`, tarball SHA-256 `be3fe4dd4cd78e61a2fc81a8bcaaad1c8f29b63ebed16f08e629a5856f0c270f`. Enables rechecking saved text, but no policy-agreement reporting located.

- **Published fixed-output extraction sensitivity (strongest prior art):** Lyu, “Same Answer, New Box: How Much of RLVR’s Out-of-Domain Gain Is Answer Format?” arXiv:2610.20639v1 (2026-10-02), `https://arxiv.org/html/2610.20639v1`, §§1–4.4 (access 2026-10-21). Quote: “On identical outputs, the largest and smallest gains ... differ by a median of 15 points.” (§1). It applies harness extractors from six public repositories to identical outputs (setup §3) and quantifies extractor-dependent benchmark gains. This directly establishes fixed-output, multi-extractor score sensitivity; its headline is model-pair gain sensitivity, not the R27 9×9 per-record verdict matrix.

- **Published per-item extraction-rule disagreement:** Berriche et al., “Benchmark Scores Are Pipeline-Dependent,” arXiv:2609.08765v1 (2026-09-08), `https://arxiv.org/html/2609.08765v1`, §§2.1, 4.4, App. G.3.1 (access 2026-10-21). Quote: “Re-scoring holds model outputs fixed and therefore isolates the effect of the modified downstream field exactly.” (§2.1). Quote: “On VSP, the final-line and anywhere extractors disagree on 30.4% of model–question pairs for which at least one rule extracts a vector.” (App. G.3.1). Table 12 says released extraction rules differed by up to 79.7 pp on identical generations (App. F). This is especially close prior art for per-item cross-policy disagreement and aggregate score shift, though it audits two domain-specific vector rules rather than a 9-policy answer-verdict matrix.

- **Additional published context:** Molfese et al., “Right Answer, Wrong Score,” Findings of ACL 2025, ACL page `https://aclanthology.org/2025.findings-acl.950/`, abstract and §5 (access 2026-10-21): compares extraction/evaluation strategies against human judgments and analyzes their score effects; its strategy-vs-human agreement is not itself policy-vs-policy verdict agreement. xFinder, arXiv:2405.11874v2, `https://arxiv.org/html/2405.11874v2`, §§5.1–5.2, compares regex extractors across harnesses and reports extraction-accuracy and ranking differences. AuditKIT, arXiv:2610.22511v1, `https://arxiv.org/pdf/2610.22511.pdf`, §§8.1–8.2: regex extraction changed model ranking on unchanged generations; per-sample scores were not retained, so it is aggregate-only. These corroborate pipeline sensitivity but are less direct than the two papers above.

- **Adjacent tools, not direct matrix prior art:** Math-Verify 0.9.0 parser supports configurable `extraction_config`/fallback in `math_verify/parser.py:573-656`; Lighteval 0.13.0 passes configurable `ExprExtractionConfig`/`LatexExtractionConfig` to a metric (`metrics/dynamic_metrics.py:159-160`). None is evidence of a cross-policy agreement report. evalmut 0.1.0 is grader mutation testing, a different construct; its GitHub README says “It never infers a hole from a verdict flip.” `https://github.com/egnaro9/evalmut`, “The honesty guarantee” (access 2026-10-21). HELM 0.5.16 search found no filter-ensemble/multiple-extractor terms; lmms-eval 0.7.3 contains the lm-eval-style `FilterEnsemble` implementation.
