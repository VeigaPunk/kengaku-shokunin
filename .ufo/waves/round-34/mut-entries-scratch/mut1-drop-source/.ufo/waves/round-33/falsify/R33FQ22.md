## 3. Findings

**F1 — C1 has no committed after-receipt; its recorded after-value lives only in prose.**
`corpus/evidence/round33/` contains only `catalogs/` and `defects-after.txt`. `SCORECARD.md:1132`
(§Round 33) records the after-line `entries=1 indexed=1 cited_rows=3 rows_present=3 rows_mined=3
usedby_ok=1 census=ok exit 0` with no receipt path — contrast rounds 29–31, which each committed
`corpus/evidence/roundNN/adoption-after.txt`. The frozen predicate is mechanically checkable (the
command reproduces at tip, and `round33_c1_verify.py` passes `checks=8 defects=0`), so the
*verifier* is runnable but the *receipt* is missing: there is no committed counter output for Q22
to require re-running at the tip. The first clause ("every receipt a claim cites must name the
revision") cannot be satisfied for C1 because there is no receipt to check.

**F2 — `defects-after.txt` names a revision at which it does not exist and at which its recorded
numbers do not reproduce.** `git cat-file -e c227e486:corpus/evidence/round33/defects-after.txt`
→ `fatal: path … exists on disk, but not in 'c227e486'` (the file was added by `7895588`). The
independent build receipt `.ufo/waves/round-33/build/receipts/defs-repro.txt` §5b (RUN H) shows the
counter on the `c227e486` tree prints `checks=6 defects=4` (N2/N5/N6 red; N1 red is archive-index
artifact). So the receipt's `# revision:` line names a commit where the quoted command prints a
different result; the numbers are true of `7895588`. The receipt is not re-derived at the revision
it names — exactly Q22's "stale debt" class, even though the tip re-run does reproduce `defects=0`.

**F3 — `catalogs/after.txt` records `entry=pending`, which is false at tip and which `--verify`
never re-derives.** At tip the knowledge entry does contain the re-probe block
(`corpus/knowledge/open-model-catalogs.md:63` `## Re-probe 2026-10-25 (round 33)`, same four
numbers). `verify()` re-derives only `hf_models/or_models/hf_schema_delta/or_schema_delta`, the
`HF missing fields:` line, and the entry block tokens; it never reads the `entry=` cell. Thus the
receipt asserts a tree state that contradicts the tip and no verifier catches it; the `--verify`
exit 0 coexists with the false cell.

**F4 — the three freeze controls name no revision and cannot re-run at tip.** `control-nothing.txt`,
`defects-before.txt`, `control-verify.txt` are historical before-state snapshots; at tip each prints
the opposite state (F-table above). Q22's first clause is literal ("every receipt a claim cites
must name the revision it was produced at") and these controls are cited by the claims
(`plans/round-33-claims.md` §§C1/C2/C3), so they fail it; Q22's second clause (final receipts only)
does not cover them. This is a documented gap in the cheap enforcement, not a "not re-run" defect in
the before-state semantics.

**F5 — `gate-receipts.txt` is descriptive, not runnable.** It records `registry=95 staged=2
collisions=0 … EXIT=0` and per-quote `ok S103/S104` lines with artifact names, but contains no
command invocation and names no revision; nothing re-runs it at tip. It is evidence for C1's
content-level gate but is not a self-containing verifiable receipt.
