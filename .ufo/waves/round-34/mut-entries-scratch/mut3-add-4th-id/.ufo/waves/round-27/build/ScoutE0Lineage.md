# E0 extraction-policy lineage

Axis: novelty. Scope: origin of last-fence + bare-fallback parsing and model format instructions.

## Findings

- `grader.py:120-134` labels the code “ports from horizon.py”; it tries the **last matching fenced block** (`blocks[-1]`) if it parses, then scans `BARE_RE` candidates in reverse and returns the last parseable candidate. At committed base `11a7fc8c64dc`, AST comparison of `extract_json_block` in `grader.py` and `corpus/evidence/round8-horizon/horizon.py` found identical function bodies. The port was introduced in round-10 commit `0c51208`; `horizon.py` first entered the repo in round-9 commit `2575be6` (round-8 files were initially working-tree-only). See `LOG.md:13,17`; `horizon.py:2,7,38-47`.

- **Documented reason for last-block selection:** round-8 critic item 10 says the then-existing `grade.sh` took the *first closed fenced block*, which could grade the wrong answer when there was preamble prose or an illustrative fence, and could conflate parse failure with state failure. Its prescribed fix was last fenced `json` block, then last balanced-brace fallback, strict `json.loads` without repair, and separate parse-failure reporting (`corpus/evidence/round8-horizon/critic-defects.md:37-39`). Round-9 critic marks #10 “landed,” describes last block plus reversed fallback, and records the parse-failure sensitivity check as moot at 0/268 (`corpus/evidence/round9-fleet/critic.md:18`). Round-9 knowledge also says the original parser choice intentionally avoids an earlier illustrative fence (`corpus/knowledge/grader-perturbation-audit.md:99-101`); round-26 lesson M42 independently refers to that choice (`corpus/lessons/round-26.md:14`). The original `grade.sh` is absent at both `~/bench-arena/grade.sh` and `~/archive/bench-arena/grade.sh` in this inspection; its first-fence behavior is documentary evidence, not a current source re-read (`corpus/knowledge/bench-arena-fresh-run.md:18-22` corroborates the description).

- **Committed model-format prompt (25 words):** “You are an evaluation target. Reply with exactly one fenced ```json code block and no other text — unless the user asks you to reply 'ok'.” (`corpus/evidence/round8-horizon/horizon.py:18-23`; file:///home/vgpnk/Projects/shokunin/kengaku-shokunin/corpus/evidence/round8-horizon/horizon.py, accessed 2026-10-21). The `call()` function prepends this SYSTEM message on every request. The same SYSTEM literal is present in r9/r11/r12 probe scripts. User prompts ask for full/final JSON state (`horizon.py:112-117,129-159,197-209`); C explicitly requests a fenced JSON row and then gives a JSON object schema (`:246-261`). No prompt chooses *first* versus *last* fence or specifies parser fallback.

- **Policy interpretation:** the instruction is a model-output format, not an extraction algorithm. E0 is the historical lane policy, critic-prescribed in round 8 and ported into the round-10 gate. E1 (first fence) is a documented predecessor behavior of `grade.sh`, but was rejected by the round-8 fix; relative to the registered E0 baseline it is counterfactual. E5 (fence-only) is a useful literal-format-only contrast, not the historical parser. E2-E4 and E6-E8 are alternative extraction policies defined for this comparison, not prompt instructions. E4's whole-output `json.loads` is specifically incompatible with the requested fenced form; E0's bare fallback is leniency for outputs that do not follow that format.

- **Census supporting the distinction:** read-only reparse of the four committed result files at the clone of base `11a7fc8c64dc` found 1,964 `raw`+`ok` records; E0 reproduced stored `got` on 1,964/1,964. 1,788 have exactly one fenced `json` block and no surrounding text; 31 are multi-fence (all r8 B records); 145 use the bare fallback. First-fence parsing changes the selected value on all 31 multi-fence records and flips 17 stored PASSes to FAIL, with 0 stored FAILs turning to PASS. This shows the E0/E1 comparison is sensitive on records departing from the single-fence instruction, not that the prompt instructed either selection rule.

- **Count caveat:** `round9-fleet/test_harness.py:313` defines “orphan” as raw ending in ``` but not starting in ```. The committed r8 bytes yield 37 by that predicate, but only 6/188 graded r8 records actually take E0's bare fallback; the other 31 are the multi-fence B records and parse by fence. Thus `round9-fleet/harness-mutation.md:122-123` overstates the 37 as fallback-only, and `round9-fleet/critic.md:36`'s 0/268 fallback claim also conflicts with a direct reparse. The exact r8 fallback raws are consistent with the prompt-format noncompliance exception, not a different instructed parser.
