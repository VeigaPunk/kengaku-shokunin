# Reverse-engineered response-extractor intent

## Reconstructed contract and evidence chain
- `corpus/evidence/round8-horizon/horizon.py:18-19` gives the model a strict response contract: exactly one fenced `json` block and no other text, except when asked to reply `ok`. `:112-117` asks inventory answers to be the exact state, every current key including zero-valued keys, integer values, any order. `:129-130,151-159` asks for the full updated state each INC turn, and for `ok`/full-state checkpoint replies in CKPT; `:164-171` asks the mono arm for the final state only.
- The shared parser at `horizon.py:38-47` first regex-matches fenced blocks, selects `blocks[-1]`, and `json.loads` that block. If absent or invalid, it scans object/array-shaped substrings from right to left, returning the first `json.loads` success; otherwise `None`. No repair is attempted. The actual fallback regex is shallow/limited-depth, not a general JSON-balancing parser.
- The reason for preferring the last block is explicit in `corpus/evidence/round8-horizon/critic-defects.md:37-39`: the prior first-fenced-block behavior could grade an illustrative fence instead of the answer; the replacement was specified to prefer the last JSON fence, fall back to a brace span, and use `json.loads` only. The source implementation also accepts an unlabelled fence and has an array fallback.
- Fallback rationale is partly inferred: the critique specifies fallback but does not explain its trigger. Later evidence shows its practical purpose: `corpus/evidence/round10-fleet/r10-mutation-sh.md:374-381` records two r9 graded raws whose fenced opener was truncated; the brace fallback recovers their bare JSON bodies. `corpus/evidence/round11-fleet/mock_server_r11.py:17-22` explicitly exercises bare-object fallback and parse failure. Confidence is high on parser semantics, medium on the original motivation for adding fallback.
- Lineage: `round9-replication/replicate.py:38-47` has the same parser. `run_r9.py:2-13,20-28` imports the scratch `replicate.py` copy, wraps calls/logging, and uses its parser at checkpoints. `round11-power/probe_r11.py:47-56` and `round12-ladder/probe_r12.py:51-60` preserve the parser. The shared system/output instructions remain at `probe_r11.py:27-28` and `probe_r12.py:31-32`.
- Round 12 family 2 adds an exact full JSON array contract, order significant, no extras/omissions (`round12-ladder/probe_r12.py:347-367`); the shared system still requires the one fenced JSON block. The Round-8 C arm instead asks for a JSON object containing `violations` and `square` (or a complete fenced JSON list in C-MONO), `horizon.py:246-260,291-296`.

## F/D family fit to the design
- The frozen family definitions/expectations are `plans/round-26-claims.md:54-73`. F1 (strip fence) and F2 (uppercase `JSON` tag) test fallback robustness, not the response format the model was instructed to produce. Fallback should recover a valid bare object/array in both cases; uppercase is not matched by the case-sensitive fence regex. This aligns with the parser's tolerant intent and later observed bare/truncated-fence recovery, but is beyond strict model-contract compliance.
- F3 (same JSON, compact/indented), F4 (dictionary key order), and F7 (CRLF) preserve parsed answer meaning. The source uses JSON decoding and exact state comparison (`horizon.py:38-47,119-123`); thus these are aligned with semantic invariance the grader ought to provide, assuming the transformed payload remains valid JSON. F4 is relevant to dict states, not ordered sequence answers.
- F5/F6 (one prose line outside the sole answer fence) leave the last fenced payload intact, so parser output should remain identical. They test tolerance to incidental surrounding text, consistent with the Round-8 critique's concern about prose/illustrative output, but such text violates the model's explicit no-other-text instruction.
- D1 is not a behavior the original extractor was meant to guarantee. It appends a second valid fenced block, while the chosen rule is specifically “take the last block”; therefore the appended previous-turn truth wins whenever it differs from the current answer. The human-reader “for reference” interpretation in the round-26 claim (`plans/round-26-claims.md:65`) conflicts with both the one-block model contract and the extractor's deliberate last-block policy. Its unchanged verdict expectation is an adversarial falsification target, not a design-supported invariance.
