The compile-time-absolute `.gcda` path, and the dual-bind / in-place-compile design.** libgcov writes `.gcda` files at process exit to the **absolute path recorded at COMPILE time**, so a binary compiled in dir X emits its `.gcda` inside the sandbox only if X exists there. The probe therefore compiles each case's build **in place under the case dir** (host side) and binds that case dir at **BOTH** `/app` and its host absolute path (writable), so the recorded compile-time path resolves inside the sandbox and lands under the `/app/sqlite` tree the grader walks (:47, :56). The `.gcno` files are different: the compiler writes them next to the object files at build time, so they are present in the case dir from the start; G4 (`-fprofile-arcs` without `-ftest-coverage`) separates the two, producing `.gcda` but no `.gcno`, so leg 3 fails on the `.gcno` assert ("No .gcno files found", :60) rather than the `.gcda` one. The frozen claims note that this compile-path behaviour is what case G4 pins, and record the pre-flight measurement — a binary copied from a foreign compile dir emits NO `.gcda` inside the sandbox — as pre-flight evidence, not a scored case. The build itself is the lane's own candidate, compiled from the pinned S233 amalgamation (`sqlite3.c` + `shell.c`): `gcc -O0 -g --coverage -o sqlite3 sqlite3.c shell.c -I. -ldl -lm -lpthread` (~4 s), placed at `/app/sqlite/sqlite3` and staged on PATH by the driver.
